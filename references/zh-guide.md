# 先复用，再新建（中文完整版）

这是 `SKILL.md` 的中文完整版，供只吃中文提示词的宿主（DeepSeek、豆包、Kimi、通义千问、文心一言、腾讯元宝、智谱清言、讯飞星火等）直接整份注入，或作为知识文件上传。两份内容等价，改规则时请同步两边。

## 核心规则

<!-- RBB:INVARIANTS:BEGIN -->
<!-- RBB:INVARIANTS:LANG: zh -->
1. **默认假设"已经有人做过"，直到检索证明没有。** 不允许"先写个雏形"再去找参考；顺序必须是 搜索 → 评估 → 决定 → 动手。
2. **默认目标是加入已有公开仓库，而不是新建仓库。** 用户想要的通常是"这个东西能用、能维护、能升级"，不是一个孤立的一次性实现；上游仓库的测试、issue 追踪、发布渠道和用户群是免费附带的资产。
3. **先证明不可复用，才允许新建。** 新建必须给出"为什么不能复用"的具体理由（许可、方向冲突、维护者已弃坑且无 fork 基础、需求本质不同），并在交付里写清。
4. **贡献必须真的有用。** 不要为了"成为作者"制造低价值 PR（错别字、格式化、无测试的重复实现）。这类提交在主流仓库会被直接关闭，且会让账号被贴上刷量标签。
5. **门禁先于代码。** 在给出候选清单与第一个可执行的贡献动作（issue 正文或 PR 草稿）之前，不得输出完整的新项目脚手架。检索到同类仓库却选择新建时，回复第一行必须写 `不可复用原因：<许可 / 方向 / 维护状态 / 需求差异>`（同时给出英文 `Not reusable because: …`，两版都留，双语用户才认得出）。

## 两条档位

| 档位 | 触发 | 动作 | 成本 |
|---|---|---|---|
| **快速档** | 用户要的是一次性小脚本、单文件工具、临时自动化 | 3 条检索串（英文功能词 + `awesome <领域>` + `<功能> alternative`），看前 5 个结果；命中明显同类就直接改造或引用，不命中才写 | 1–2 分钟 |
| **完整档** | 新建库/插件/服务/长期维护的项目，或快速档命中同类 | 走下面四步全流程 + 六维打分 + 贡献路径 | 10–30 分钟 |

快速档不是"可以跳过检索"的借口：省的是打分与贡献流程，不是省"先看有没有人做过"。它的回复固定三行，不套第 4 步的四段模板：

```text
复用：<仓库>（<许可>，<star 数>）——<一句话说明为什么合用>
改动：<在那个仓库改什么 / 直接调用什么>
风险：<判断错了会坏在哪>
```

0 命中要单独说明，并列出实际跑过的检索串——让用户看到"查过但没有"，而不是默认相信这个结论。

## 第 1 步：发现

按 [discovery-playbook.md](discovery-playbook.md) 执行，最少三轮：

- **轮 1 功能直搜**：GitHub 仓库搜索 + 关键词同义扩展（不要只用用户原话，务必翻成英文再搜）。
- **轮 2 生态搜索**：包管理器（npm / PyPI / crates.io / Maven / Homebrew）、awesome-list、框架官方插件目录、Docker Hub。
- **轮 3 人的搜索**：仓库 issue/discussion 里是否有人提过同样需求；Stack Overflow / HN / Reddit / V2EX / 知乎是否有同类讨论并指向某个仓库。

把候选整理成 3–6 个仓库的短名单，每个记录：全名、star 数、最近提交时间、许可证、缺什么。**没有联网或仓库访问能力时**，不要编造仓库；输出一份"待用户确认的检索清单"，让用户提供候选或开启联网，再继续。

有 `gh` CLI 且已登录时，先用脚本拿到粗筛表：

```bash
python scripts/repo_scan.py "video highlight clip" "auto cut shorts" --stars 100
```

## 第 2 步：评估

用 [repo-triage.md](repo-triage.md) 的六维打分（活跃度、维护者响应、许可兼容、贡献友好度、需求匹配度、工程质量），每维 0–2 分，得出一个结论：

| 结论 | 条件 | 下一步 |
|---|---|---|
| **Join（首选）** | 总分 ≥ 8，许可允许，需求能作为增量功能/修复并入 | 走贡献流程 |
| **Extend（次选）** | 核心不接收该功能，但仓库有插件/扩展/主题机制 | 以官方扩展形式发布，仍算加入生态 |
| **Fork（兜底）** | 维护者失联、方向冲突、许可允许 | fork 后保持上游同步，并把改进 PR 回上游 |
| **Build（例外）** | 无同类项目、许可禁止、需求本质不同 | 新建，但先说明理由 |

对被否掉的候选，写一句"为什么不用它"。用户会追问这个。

## 第 3 步：加入

按 [contribution-protocol.md](contribution-protocol.md) 的固定顺序：

1. **读** `CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、PR 模板、commit 规范、是否有 CLA/DCO。
2. **Issue 先行**：bug 修复类可直接 PR；新增功能、行为变更、重构类必须先开 Issue 或 Discussion 拿维护者的"可以做"。
3. **小 PR**：单一目的、尽量 <300 行 diff、带测试、带文档、带 changelog、签名 `Signed-off-by`（若仓库要求）。
4. **说清 AI 参与**：代码由 AI 协助时在 PR 里如实说明协助范围；作者身份用用户自己的 GitHub 账号，不冒用他人。
5. **跟进**：不改 Review 意见之外的东西，不催更，7 个工作日无回应礼貌 bump 一次；合并后跟进 release 与 follow-up。

若被拒或长期无人响应，按结论表降级到 Extend / Fork，不要反复重开同一个 PR。

## 第 4 步：交付

**完整档**给用户的回复必须包含这四段，缺一不可（快速档用上面那三行，不走这个模板）：

```markdown
## 找到了什么
| 仓库 | star / 最近提交 | 许可 | 与需求的差距 |
## 为什么选它
## 我要加的东西（Issue / PR 计划）
- 目标文件、改动范围、测试方式、预期 diff 规模
## 备选与风险
- 被拒时的降级路径；许可与商标边界；维护者活跃度风险
```

## 什么时候不该复用

出现以下任一条，直接进入新建并把理由写进交付：

- 用户明确要求私有、闭源、不得上传、公司内部资产。
- 目标仓库许可证与用户用途冲突（如闭源商用 + AGPL、无商业使用条款）。
- 仓库要求 CLA 转让版权，而用户不接受。
- 需求与仓库方向相反（对方明确声明不做这类功能），或维护者已公开弃坑且无活跃 fork。
- 仓库安全状况不可接受（无维护、已知高危漏洞、来源可疑）。

## 硬约束

- **不虚构仓库、star 数、提交时间、许可证。** 无法核实时标注"未核实"。
- **不在未读 CONTRIBUTING 的情况下提交 PR**，不绕过 PR 模板，不做 force-push 到他人分支。
- **不以"AI 批量生成"作为提交理由**，不一次向多个仓库投同类低质 PR。
- **不把用户私有代码贴到公开 Issue/PR**，需要复现时最小化并脱敏。
- **每一次公开写都要逐次确认**：开 issue、开 PR、发评论都是公开且难撤回的动作，不属于"skill 让我贡献"的授权范围。把完整正文（PR 还要带 diff）交给用户，得到这一次的明确同意再提交。本机 `gh` 已登录、带 `repo` scope，不等于得到许可。
- 不代替用户点击"发布/合并"这类不可逆外部动作，PR 提交前把 diff 与说明交给用户确认。

## 宿主落位

四类：Skill 目录 / 仓库规则文件（AGENTS.md 等）/ 聊天自定义指令 / 自建 Agent system prompt。完整平台清单与规则文件名见 [host-adapters.md](host-adapters.md)。

## 自适配：改包装，不改规则

宿主期待的形态可能和这份文件不一样——换一套 frontmatter、只吃一段扁平的系统提示、要 JSON 工具定义、要另一种语言、要插件清单、上下文预算更小。**首次使用时可以改包装，但不能改规则。**

**不可变项（换什么容器都要原样保留）：** `<!-- RBB:INVARIANTS:BEGIN -->` 与 `<!-- RBB:INVARIANTS:END -->` 之间那段是正典，`localization.contract.json` 存着它的 SHA-256。逐字搬运→哈希吻合（`verbatim` 模式）；宿主要求换语言时，块照样用标记圈住，但第一行加 `<!-- RBB:INVARIANTS:LANG: <语言码> -->`（哈希必然不吻合→`translated` 模式，改用语义锚点判）。不许重新编号、合并或删掉任何一条。

- 五条核心规则，包括门禁，以及 `不可复用原因 / Not reusable because:` 那一行。
- 结论顺序：Join → Extend → Fork → Build；Build 必须写明理由。
- 四段交付（找到了什么 / 为什么选它 / 我要加什么 / 备选与风险）。
- 快速档的三行格式（`复用` / `改动` / `风险`），用到快速档时必须保留。
- 硬约束，尤其是：不虚构仓库与 star 数、不读 CONTRIBUTING 不提 PR、不把私有代码贴到公开处。

**可以改（这些属于格式，不属于含义）：**

- frontmatter 的字段与顺序：宿主要什么就填什么（`name`/`description`、`title`/`when_to_use`、`tools`、`version`），宿主不认的字段直接删。
- 文件布局与命名：合成一段扁平提示、放 `rules/reuse.md`、写进插件清单，或塞进 memory；`references/` 按宿主的加载方式合并或拆分。
- 引用方式：相对路径改写成宿主自己的资源语法；宿主打不开文件就把被引用的那几节内联进去。
- 语言：翻成宿主的工作语言，但门禁那句中英都留，方便双语用户认出。
- 工具绑定：`gh` CLI ↔ 宿主的 GitHub 工具/MCP ↔ 纯 `web_search`，并写清这个宿主实际有哪一个。
- 压缩程度：精简版 / 完整版 / 分节版都行，但不得低于不可变项。

**每个宿主做一次，五步：**

1. **识别**：读宿主的官方文档，或读它已有的两个 skill，列出它的约定：frontmatter 字段、文件布局、资源怎么加载、上下文预算、可用工具、输出语言。
2. **对照**：写一张小表：本 skill 的形态 → 该宿主的形态，动到的每个元素一行。
3. **重写**：产出本地化副本。宿主允许并存文件时保留原件，方便用户 diff。
4. **验证**：运行 `python scripts/verify_localized.py <本地化副本>`，必须打出 `PASS`；不通过就改，改完再跑一次。某条在宿主上确实活不下来（无文件系统、无工具），在声明里显式写 `unsupported on this host` 并按 host-adapters 的降级表处理，**不许静默删掉**。校验器故意放在模型外面：你说"我保留了规则"不算证据。
5. **声明**：文件最后一个非空、且不在代码围栏内的行（末尾追加版权/生成时间不算错），以及回复的最后一行，必须是

```
localized: host=<名称> | kept=<原样保留的不变项> | changed=<改动的包装项> | unsupported=<做不到的项及原因，没有就写 none>
```

没有这一行、也没有 `PASS`，就不算做完，更不能说"这就是同一个 skill"。

自适配是最后一公里的打包动作，不是重写流程的许可。如果宿主约定逼出真正的语义变更，说出来并询问，不要悄悄发一个被削弱的版本。
