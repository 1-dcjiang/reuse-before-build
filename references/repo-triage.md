# 候选仓库评估：六维打分与决策

对短名单里每个仓库打分，每维 0–2 分，满分 12。评分依据必须来自实际读到的仓库数据（提交时间、issue 回复、CONTRIBUTING、CI 状态、许可证文件），不能靠印象。

## 六维定义

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| **活跃度** | 最近提交 > 12 个月，或已 archive | 3–12 个月内有提交，无 release | 90 天内有提交且有 release/tag |
| **维护者响应** | issue 常年无人回复，或只有单人且失联 | 有回复但周期 > 30 天 | 近 30 天有 maintainer 回复/合并 |
| **许可兼容** | 无许可证 / 与用户用途冲突 | 有许可但需注意（如 GPL 用于闭源分发、无商业条款） | MIT / Apache-2.0 / BSD 等宽松许可，或用途与许可一致 |
| **贡献友好度** | 无 CONTRIBUTING，PR 常被无理由关闭 | 有 CONTRIBUTING 但无 issue 模板/无 good first issue | 有 CONTRIBUTING + PR 模板 + CI + 明确 review 流程 |
| **需求匹配度** | 功能只覆盖 < 40%，或方向相反 | 覆盖 40–70%，差的正是要加的部分 | 覆盖 ≥ 70%，增量明确、接口已就位 |
| **工程质量** | 无测试、无 lint、单文件堆代码 | 有测试但覆盖薄 | 有测试 + CI + 类型/文档 + 清晰模块边界 |

**结论：**

- 总分 ≥ 8 且许可 ≥ 1 → **Join**
- 总分 6–7，或功能匹配 < 40% 但仓库有插件机制 → **Extend**（做官方扩展）
- 总分 ≤ 5，但方向对、许可允许、只是维护者不活跃 → **Fork**（在 fork 上改，改进仍 PR 回上游）
- 无同类项目 / 许可禁止 / 方向相反 → **Build**

分数只用于排序和给用户解释，不要为了凑够 8 分抬高评分。低于阈值时如实说"这个仓库不适合作为上游"。

## 许可证速查

| 许可 | 用于自己闭源产品 | 向上游提交 | 备注 |
|---|---|---|---|
| MIT / BSD / ISC | 可以 | 可以 | 保留版权声明 |
| Apache-2.0 | 可以 | 可以 | 需保留 NOTICE，注意专利条款 |
| MPL-2.0 | 可以（改动文件需开源） | 可以 | 文件级 copyleft |
| LGPL-2.1/3.0 | 动态链接一般可以 | 可以 | 修改库本体需开源 |
| GPL-2.0/3.0 | 分发即需整体开源 | 可以 | 常用于 CLI 工具 |
| AGPL-3.0 | 提供网络服务也触发开源 | 可以 | SaaS 场景最大的坑 |
| 无 LICENSE | **不可以**复制/分发 | **不可以**提交（默认保留所有权利） | 只能提 issue 建议，不能带代码 |

许可不明确时（README 写"free to use"但没有 LICENSE 文件），按"无许可"处理，并在交付里提示用户让维护者补 LICENSE。

## 红旗清单（命中即降级或放弃）

- 仓库已被 archive，或 README 明写 "no longer maintained" 且没有活跃 fork。
- 单一维护者 + 大量未处理 issue + 6 个月无提交。
- 明确声明 "AI-generated PRs will be closed"（要尊重，不然等于自毁账号）。
- 有 CLA 要求把版权转让给公司/个人，而用户不愿签。
- 仓库内已有同类 PR 长期挂起（说明这条路走不通，换 Extend/Fork）。
- 星数虚高但 issue 区大量"不能用/已弃坑"反馈。

## 读代码的最小动作

决定 Join 之前，至少完成：

1. 读 `README` 的 Usage/Architecture 部分，确认功能缺口不是"作者故意不做"。
2. 读 `CONTRIBUTING.md` 与最近 5 个已合并 PR 的形态（diff 大小、是否带测试、review 轮次）。
3. 定位你要改的文件与函数，确认接口能容纳你的增量，不需要重构核心。
4. 跑通一次本地安装与测试（`make test` / `npm test` / `pytest`），确认基线是绿的。

基线跑不绿时，先修基线再谈功能——把"仓库当前测试失败"写进 issue，这本身就是一条有价值的贡献。
