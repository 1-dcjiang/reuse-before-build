# 四种结论的交付形态

示例都是"用户提出一个功能请求"的场景。照最接近的一个写，别自创格式。

## 例 1 · Join（最理想）

> 用户："帮我写一个把长视频自动切成短视频的工具。"

**检索结果**：`owner/autoclip` ★4200，90 天内 6 次提交、最新 release 两周前，MIT，已有 ffmpeg 切片与静音检测，**缺"基于字幕挑高光片段"**；issue #212 有人提过同样需求，维护者回了 "PRs welcome"。

**结论**：Join。交付形态：

```markdown
## 找到了什么
| 仓库 | ★ / 最近提交 | 许可 | 与需求的差距 |
|---|---|---|---|
| owner/autoclip | 4200 / 2026-10 | MIT | 已有切片+静音检测，缺字幕驱动的高光挑选 |
| other/clipbot | 890 / 2025-12 | GPL-3.0 | 全功能但闭源商用受限，且半年无提交 |

## 为什么选它
issue #212 已确认这个需求且维护者明确欢迎 PR；接口 `ClipPlanner` 已预留，改动可控制在 2 个文件。

## 我要加的东西
- 新增 `src/planner/transcript_highlighter.py`，复用现有 `ClipPlan` 数据结构
- 测试：`tests/test_transcript_highlighter.py`（3 个用例：单高光、多高光、字幕缺失回退）
- 文档：README 的 Options 表加一行；CHANGELOG 加 Unreleased 段
- 预计 diff ~180 行；先在该 issue 下回复"我来实现"，再提 PR

## 备选与风险
- 若维护者要求换接口：改为插件式 `planner` 注册，不碰核心
- other/clipbot 的 GPL-3.0 不适合闭源分发，不用
```

## 例 2 · Extend（核心不收，但仍进生态）

> 用户："给我做一个 VS Code 里自动整理 import 顺序的插件。"

**检索结果**：同类功能已被 `eslint-plugin-import` 覆盖；VS Code 市场里已有一个 800 安装量的同类插件，MIT，但两年没更新。**最省事的路线是给那个挂掉的插件提 PR/接 fork，或按官方扩展点做一个能被上游推荐的插件。**

**结论**：Extend。交付形态要点：

- 明确"不做第 N 个同款插件"，先给原插件提修复 PR 或 issue。
- 若原插件作者不回应：fork 后发布时**换名并注明 derived from**，README 写清与上游的差异，保留上游 LICENSE 与版权声明。
- 在插件市场描述里写明"上游 X 的维护分支"，这是被生态接受的最快方式。

## 例 3 · Fork（维护者失联）

> 用户："这个库不支持 Python 3.13，能改一下吗？"

**检索结果**：目标库 `owner/libx` ★1800，最后提交 2024-06，issue 里 30+ 条同类抱怨，无 maintainer 回复；MIT 许可允许 fork。

**结论**：Fork。交付形态要点：

- fork 命名 `<原库>-modern`，README 首行注明上游链接与 fork 原因。
- 只做兼容性最小改动，不加新功能（减少 rebase 成本）；加 `upstream` remote，每月 rebase。
- 仍向上游提一次 PR（哪怕很可能没人看），这样被合并时可直接回落；被合并则把 fork 归档。
- 交付里明确告诉用户"这个 fork 现在由你维护"，不要假装它是官方项目。

## 例 4 · Build（例外，必须写明原因）

> 用户："我们公司内部要一个把工单系统数据同步到内网数据库的 Daemon，代码不能外传。"

**结论**：Build。原因行必须出现在回复开头：

```markdown
不可复用原因：私有/闭源要求（公司内部资产，代码不得上传）；候选 owner/ticketsync（MIT）功能匹配 80%，但接入方要求源码不外流，因此不 fork、不提 PR，只在本机实现。
```

后续仍要做两件事：一是**本地私有实现里尽量复用公开库**（以依赖形式引入 MIT/Apache 组件，而不是抄代码）；二是把"哪些部分可私有、哪些必须依赖开源"分开写进交付。

## 反例（不要这样写）

```markdown
好的，我为你写了一个完整的 autoclip 工具，包含 12 个模块和 CLI，共 1400 行代码。
```
— 没检索、没候选、没理由，直接违反门禁规则 5。
