# 接入口与薄适配层：让接入点难被上游改动打断

复用别人的仓库，真正的风险不在"今天能不能跑"，而在**上游下一次改动会不会把你的接入打断**。结论是两条：

1. **只从"上游承诺稳定"的口子接入**，不要从内部实现接入。
2. **把所有对上游的调用收进一个薄适配层**，业务代码不直接碰上游。

## 一、接入口的优先级（从高到低）

| 优先级 | 接入口 | 为什么 | 注意 |
|---|---|---|---|
| 1 | 官方插件 / 扩展 / 钩子机制（plugin API、hooks、events） | 上游公开承诺给第三方用，破坏它等于破坏生态 | 按官方文档注册，不绕注册表 |
| 2 | 公开库 API（导出函数/类，带 semver 与 CHANGELOG） | 有版本承诺，破坏会体现在 major 版本 | 钉版本区间，升级前读 CHANGELOG |
| 3 | CLI / stdio / 配置文件 schema / HTTP API | 进程级边界，内部重构不影响你 | 解析输出要容错，字段缺失不崩 |
| 4 | 事件 / webhook / 消息队列 | 天然解耦 | 处理重复投递与乱序 |
| 5 | 内部函数、私有模块、monkey-patch、改 node_modules / site-packages | **没有稳定性承诺** | 只作一次性验证，**不得作为交付方案** |

**接入口不存在时的正确动作**：给上游提一个"公开接口/钩子"的 PR（小、带测试、说明使用场景），让口子变成上游承诺的一部分；在此之前用优先级 3/4 的进程级边界顶着，而不是直接 patch 它的内部函数。

## 二、薄适配层的写法

- **单独一个模块**，命名能一眼看出用途：`upstream_adapter.py` / `UpstreamAdapter.ts`。放在你自己的仓库里，不放进上游。
- **只做翻译**：上游的数据结构 ↔ 你的数据模型、上游的异常 ↔ 你的异常、上游的调用约定 ↔ 你的函数签名。**不写业务逻辑**。
- **体量上限约 150 行**。超过就说明业务逻辑正在漏进适配层，拆出去。
- **单向依赖**：业务代码只 import 适配层；适配层 import 上游；上游不 import 你。
- **业务代码里禁止出现上游内部路径**（`upstream/src/internal/...`、`upstream._private`）。只允许出现适配层 re-export 的公开符号。
- **版本钉住 + 契约测试**：为适配层写一组 contract test，断言"我依赖的上游行为仍然成立"（签名、返回结构、关键语义）。上游升级 = 跑这组测试，红了只改适配层。

## 三、验收（不满足就不算接完）

1. **替换测试**：把上游换成 mock/stub，你的业务测试应当仍然全绿——这证明业务逻辑没有长在上游身上。
2. **隔离检查**：`git grep -n "from upstream\|require('upstream\|import upstream" -- ':!*adapter*'` 应当没有业务代码命中（按实际上游包名替换）。
3. **升级演练**：把上游升一个 minor 版本跑一遍，若只有适配层需要改，说明口子选对了；若业务代码也要改，说明适配层漏了。
4. **写进交付**：接入口属于上表哪一级、适配层文件路径、行数、契约测试怎么跑。用户有权知道"上游一动我哪里会疼"。

## 四、反模式

- 在业务代码里到处 `import upstream.internal`，出了事全仓库都要改。
- 为了省一个文件，把适配逻辑写进业务函数里，"反正就几行"。
- 直接修改上游源码再打包（fork 补丁藏在构建脚本里），升级即丢失。
- 用 monkey-patch 修上游 bug 而不回提上游：既脆弱，又剥夺了生态变好的机会（违反本 skill 的 Join 原则）。
